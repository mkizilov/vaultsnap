# S3-compatible repositories

A VaultSnap repository can live in a bucket of any S3-compatible service (AWS S3, MinIO, and
others) instead of a directory:

```sh
export AWS_ACCESS_KEY_ID=...          # from the standard AWS credential chain; see Credentials
export AWS_SECRET_ACCESS_KEY=...
vaultsnap --repo s3://my-bucket/laptop init
vaultsnap --repo s3://my-bucket/laptop backup ~/Documents
vaultsnap --repo s3://my-bucket/laptop snapshots
vaultsnap --repo s3://my-bucket/laptop restore 3f9a --target ~/restored

# an S3-compatible server on this machine
vaultsnap --repo s3://my-bucket --s3-endpoint http://127.0.0.1:21100 snapshots
```

Every command works the same as on a directory. The format is the same too: the objects in the
bucket are exactly the files of a directory repository ([`FORMAT.md`](FORMAT.md)), so a repository
can be copied between a directory and a bucket with any tool that copies objects, with no
conversion. How the backend fits the storage interface, and why, is in [`STORAGE.md`](STORAGE.md);
the threat model is in [`SECURITY.md`](SECURITY.md).

## Location and options

`--repo s3://BUCKET[/FOLDER]`. The bucket must exist; VaultSnap does not create buckets. The
optional folder (`/`-separated names of letters, digits, `.`, `_`, `-`) is a key prefix, so several
repositories can share a bucket. Bucket names follow the S3 rules (3 to 63 characters of lowercase
letters, digits, hyphens, and dots).

| Option | Environment | Meaning |
|---|---|---|
| `--s3-endpoint URL` | `VAULTSNAP_S3_ENDPOINT` | The service URL for an S3-compatible service. Default: AWS (or what the SDK reads from `AWS_ENDPOINT_URL_S3` / `AWS_ENDPOINT_URL`). |
| `--s3-region REGION` | `VAULTSNAP_S3_REGION` | The region to sign for. Default: the AWS configuration (`AWS_REGION`, the profile), else `us-east-1`. **Set one for any service that is not AWS:** without any, the SDK first asks the instance-metadata service, which prints a `failed to load region from IMDS` warning on every command and costs a request (measured: about 0.1 s more per command against a local server; on a network where that address hangs it was not measured). |
| `--s3-profile NAME` | `VAULTSNAP_S3_PROFILE` | A named profile of the shared AWS config and credentials files. Default: `AWS_PROFILE`, else `default`. |
| `--s3-path-style BOOL` | `VAULTSNAP_S3_PATH_STYLE` | `https://host/bucket/key` instead of `https://bucket.host/key`. Default: true with `--s3-endpoint`, false for AWS. |
| `--s3-ca-bundle FILE` | `AWS_CA_BUNDLE` | A PEM file of the certificate authorities to trust instead of the system's, for a private CA. |
| `--s3-allow-insecure-http` | | Accept an `http://` endpoint that is not on this machine. |
| `--s3-max-requests N` | `VAULTSNAP_S3_MAX_REQUESTS` | The most requests in flight at once. Default 8, at most 256. |

Everything that can be refused without a network is refused before connecting, with nothing
created on disk: a bad bucket name or folder, a plain `http://` endpoint on another machine, an
endpoint that contains a user name or password, a request limit outside 1 to 256.

Timeouts (10 seconds to connect, 5 minutes for one request) and the retry policy are fields of
`S3Config` in the library and have no command-line options.

## Credentials

There is **no option for credentials**, deliberately: a secret on a command line shows up in
process lists and shell history. They come from the standard AWS credential chain: the environment
(`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`), the shared `~/.aws/config` and
`~/.aws/credentials` files and their profiles, SSO, web identity, and container and instance roles.
VaultSnap's code never reads, stores, or formats a credential:

* an endpoint URL that contains one is refused, and the message does not repeat it;
* the `Debug` output of the configuration omits everything that could carry one, and shows an
  endpoint without any user information;
* text that comes back from the service or the network is cut to 600 characters and anything that
  looks like an AWS access key id is replaced before it can reach an error message;
* the HTTP stack and the AWS SDK are limited to warnings unless `RUST_LOG` says otherwise, because
  they can log request details at debug and trace level. `-v`, `-vv`, and `-vvv` raise only
  VaultSnap's own messages. Whoever sets `RUST_LOG=trace` asks for everything and gets it.

The repository passphrase is a separate secret with its own rules ([`CLI.md`](CLI.md)). The AWS
credentials are the one secret that VaultSnap's own encryption does not cover.

## Encryption stays on this side

The backend is only ever handed bytes that were sealed by the layers above it: chunk objects,
snapshot files, key files. There is no code path that uploads anything else. What the bucket
holds, readable by whoever can read the bucket:

* `config` (format version, repository id, creation time), lock files (kind, process id, time),
  and the plaintext headers of the other objects (magic, version, kind, compression, length);
* the **names** of objects: random chunk and snapshot ids, which say nothing about the data;
* the **sizes** of objects (a chunk's size, roughly its compressibility), their **number**, and
  **when** each was written ([`SECURITY.md`](SECURITY.md)).

File names, paths, contents, host names, and tags are inside encrypted objects. The integration
test `nothing_readable_is_uploaded` reads back every object of a repository and looks for a
plaintext marker, a file name, a host name, the passphrase, and file content.

## Transport security

Certificates and host names are always verified (rustls). There is no option to turn verification
off. A private CA is trusted with `--s3-ca-bundle` (or `AWS_CA_BUNDLE`), and then trusted
*instead of* the system's. Checked by hand against MinIO serving HTTPS behind a generated CA
([`RELIABILITY.md`](RELIABILITY.md) section 5): a missing or unrelated CA is refused with
`UnknownIssuer`, the right one works for `init`, `backup`, `check --read-data`, and `restore`, and a
host name the certificate does not carry is refused. Those cases are not automated tests yet
(roadmap item 12), and a certificate from a public CA, the usual case with AWS, could not be tried.
The HTTP client is the current one (hyper 1.x, rustls 0.23 with aws-lc); the SDK's legacy client
(hyper 0.14, rustls 0.21) is not compiled in, because it drew security advisories. Plain `http://` is accepted only for `localhost`, `127.0.0.0/8` and
`[::1]`, and for other hosts only with `--s3-allow-insecure-http`: it exposes object names, sizes,
and timing to the network, and lets it withhold data (it cannot alter data undetected).

## Consistency, conditional writes, and checking them

VaultSnap's safety rests on three guarantees ([`STORAGE.md`](STORAGE.md)): a write is visible to
every later read and listing (read-after-write), creating an object only if it does not exist is
exclusive for all clients, and an object appears whole. AWS S3 provides all three. Other services
may not: some ignore `If-None-Match` and overwrite.

So the backend **checks** instead of assuming. When it connects it reaches the bucket (`HEAD
bucket`), then creates an object named `vaultsnap-probe-<random>` twice with `If-None-Match: *`,
tries a replacement with a stale `If-Match` and one with the current ETag, tries an `If-Match`
update of an object that does not exist, and deletes what it created. It declares to the repository
only what it saw work. A service whose second create succeeds is refused with a message, before
anything is written to the repository. A service that fails only the conditional *replace* (the
MinIO release of April 2025 creates the object on `If-Match` of a missing one, where S3 answers
`404`) is still accepted, because a repository uses only the exclusive create, but it is given no
conditional-replace guarantee. A user who is not allowed
to write at all (a read-only key) gets the guarantees of S3 assumed, since credentials that cannot
write cannot break exclusivity either; listing, checking, and restoring then work if the lock
files allow it, and any command that writes fails with `access was refused`.

Each connection therefore costs a handful of requests and leaves nothing behind. If the delete
fails, a warning names the probe object and it can be removed by hand.

## Retries

The AWS SDK's own retries are switched off. VaultSnap's `RetryingBackend` wraps the S3 backend
instead, so that it sees every attempt:

* **What is retried:** connection errors and timeouts, a response that breaks off, `5xx`, `408`,
  `429`, `SlowDown` and the other throttling codes, and `409 ConditionalRequestConflict` (a
  concurrent conditional write on the same key; the retry gets its real answer).
* **What is not:** `403` and other refusals, a missing bucket, a failed precondition, and anything
  else that waiting cannot fix. Missing credentials are reported as a refusal, not retried.
* **Backoff:** exponential with jitter. Default: 5 attempts, waiting about 0.1, 0.2, 0.4 and 0.8
  seconds (each between half and all of that), at most 5 seconds.
* **A write whose answer was lost** (the request reached the service, the response did not) is not
  guessed at. A retried `Create` that finds the object already there, or a retried `Update` that
  finds a version other than the one it expected, reads the object and counts as done only if it
  holds exactly the bytes being written. That cannot be mistaken for another writer, because every
  writer in VaultSnap writes data unique to it: a random lock name, a snapshot id, a freshly
  sealed chunk. A retried delete that finds the object gone has succeeded.

A transfer that still fails after the retries ends the command with an error. For a backup that
means no snapshot is published; see the next section.

## Interrupted backups and resuming

The order of writes is the one in [`BACKUP.md`](BACKUP.md), unchanged by the backend: every chunk
is uploaded, then the snapshot file is created in a single conditional `PUT`. A snapshot exists in
the bucket only if every chunk it names did when it was committed, and an interrupted or failed
backup (Ctrl-C, a network outage, a crash) publishes nothing.

What an interrupted backup leaves is the chunks it had already uploaded. The next backup finds
them (a chunk's object name is derived from its content) and does not upload them again; the
report counts them as existing chunks. Uploads are not resumed *inside* a chunk: chunks are at most
a few megabytes, so at most the chunks in flight are sent twice.

One thing is left behind that a person must clear: the **lock file** of a process that was killed
(rather than cancelled) stays in `locks/`. Shared locks, taken by `backup`, `check`, `restore` and
the listing commands, do not conflict with each other, but a stale one blocks `prune`, which needs
the exclusive lock. After checking that no VaultSnap process is running, delete the file named in
the error message, for example `aws s3 rm s3://my-bucket/laptop/locks/<name>.lock`.

## Bounded resources

At most `--s3-max-requests` calls are in flight, whatever `--jobs` says, and a caller that has to
wait for a free slot blocks. Memory is bounded by roughly that many objects (a chunk object is at
most the maximum chunk size, 4 MiB by default, plus a few dozen bytes; a snapshot file is held
whole). The S3 client runs on a runtime of two threads of its own and reuses connections.

## Request volume and cost

Object stores bill and rate-limit by request, and VaultSnap stores each chunk as one object:

* A backup issues one `HEAD` for each chunk it stores (to see whether the object exists) and a
  conditional `PUT` for each new one. Committing the snapshot then checks every distinct chunk it
  names with one more `HEAD`, one after the other, and a file reused from the previous snapshot
  is checked the same way. A backup of a very large tree to a distant service therefore spends
  much of its time waiting for those `HEAD`s; replacing them with a listing is future work.
* `check` and `prune` list `data/` (256 shard prefixes) and `prune` deletes one object per request.
* Small chunk sizes mean many requests. The default (256 KiB minimum, 1 MiB average, 4 MiB
  maximum) is a compromise between deduplication and request count.
* There is no multipart upload: every object is one `PUT`. That is possible because chunk objects
  are small and a snapshot file is capped at 1 GiB, far below the 5 GiB limit of a single `PUT`.
* Packing chunks into larger files would cut the request count a great deal. It is future work and
  a format change ([`STORAGE.md`](STORAGE.md)).

## Limits and non-goals

* Anyone with write access to the bucket can delete snapshots or roll the repository back to an
  earlier consistent state, undetected ([`SECURITY.md`](SECURITY.md)). Bucket versioning and object
  lock are not used, nor needed for correctness; they can add protection of their own.
* There is no append-only mode: `prune` deletes through the same credentials as `backup`.
* ETags are used as opaque version tokens. A service that returns no ETag is refused.
* Server-side encryption, storage classes, and lifecycle rules are the operator's business. An
  archive storage class that makes objects slow to read will make `restore` and `check --read-data`
  fail or stall.
* The clock matters: requests are signed with the local time, and a skew of more than a few
  minutes makes the service refuse them (the message says to check the clock).
* The MinIO project, on which the integration tests are written, was archived by its owner on
  25 April 2026; this document makes no claim about its future releases.

The integration tests run only when `VAULTSNAP_S3_TEST_ENDPOINT` names a server; without it each
one prints `SKIPPED (unverified)` and passes, and a skipped test proves nothing.

### Running them without Docker

MinIO stopped publishing binaries when its project was archived, so `scripts/minio-local.sh` builds
the pinned release from source with a checksum-verified Go toolchain, entirely inside the repository
(`.agent-local/tools`, or `$VAULTSNAP_TOOLS`), and serves it on loopback with random credentials:

```sh
sh scripts/minio-local.sh install      # once: Go and MinIO, about two minutes, two build workers
sh scripts/minio-local.sh start        # 127.0.0.1:21100 (console 21101), bucket vaultsnap-test
eval "$(sh scripts/minio-local.sh env)"
CARGO_BUILD_JOBS=2 cargo test -p vaultsnap-core --test s3_minio -- --test-threads=2
sh scripts/minio-local.sh clean        # stop the server, delete its data and credentials
```

`stop` and `clean` ask the server itself whether it is still running and fail with a message if it
is, rather than trusting that a signal worked. In a sandbox that does not let one command signal a
server another command started, run `start`, the tests, and `clean` in the same command, or start
the server as a task whose owner can stop it.

Go keeps its module cache read-only; to delete the tools directory, `chmod -R u+w` it first.

### Running them with Docker

```sh
export AWS_ACCESS_KEY_ID=minio-test-user              # any user name
export AWS_SECRET_ACCESS_KEY=minio-test-secret-value  # at least 8 characters
docker compose -f docker/minio/compose.yaml up -d      # S3 API on 127.0.0.1:21100
curl -fsS http://127.0.0.1:21100/minio/health/ready    # wait until this succeeds
export VAULTSNAP_S3_TEST_ENDPOINT=http://127.0.0.1:21100
CARGO_BUILD_JOBS=2 cargo test -p vaultsnap-core --test s3_minio -- --test-threads=2
docker compose -f docker/minio/compose.yaml down -v   # stop the server and delete its data
```

This path **was never run**: Docker was not available where this was developed, and whether that
image tag is still pullable was not checked.

`VAULTSNAP_S3_TEST_BUCKET` names another existing bucket (default `vaultsnap-test`, which both ways
of starting MinIO create). Every test uses a prefix of its own and removes it when it ends; a test
that panics can leave objects behind. The outage test starts a small forwarder on a loopback port
from 21150 to 21199 and cuts it on purpose; the refused-connection test uses a free port from
21110 to 21149.

### What is verified

On macOS (Apple silicon) with Rust 1.94.1, against the MinIO release `RELEASE.2025-04-22T22-12-26Z`
built from source and running on loopback over plain HTTP:

* all 7 tests of `s3_minio.rs` pass, through the real AWS SDK adapter (`storage/s3/sdk.rs`): the round
  trip and restore from a fresh connection, no readable data uploaded, duplicate uploads (including
  eight racing writers of one chunk: exactly one creates it), a cancelled backup that publishes
  nothing and is resumed, a network outage in the middle of a backup (the forwarder is cut on
  purpose), connection failures with no credential in any message, and the **whole storage contract
  (22 cases)**. Pointed at a port with nothing on it, 5 of the 6 other tests fail, so they do use the
  server;
* running the contract against a real server found one discrepancy (the `If-Match` behavior above),
  which is why the connect-time probe now tests it;
* the toolchain pin of 1.94.1 builds the SDK crates with the committed `Cargo.lock`.

**Not verified:** AWS S3 itself; TLS, including a private CA bundle; named profiles, SSO, and role
credentials; request signing for a real region; throttling and `SlowDown` handling; other
S3-compatible services; anything on Linux; and the Docker path above.
